## Creating a release

A release is triggered by pushing a version tag to the main branch. The tag must start with `v` followed by a semver version number.

```bash
git checkout main
git tag v0.1.0
git push origin v0.1.0
```

This triggers the CI workflow, which builds binaries for all five platforms, runs the test suite, and creates a GitHub release with the artifacts attached.

## How the CI workflow works

The workflow at `.github/workflows/cross-platform-build-test.yml` runs on every `v*` tag push. It does the following:

For each platform (linux-x86_64, linux-aarch64, macos-x86_64, macos-aarch64, windows-x86_64):

1. Extracts the version number from the tag (e.g., `v0.1.0` becomes `0.1.0`).
2. Runs the test suite with `-Dtest=true -Dversion=<version>`.
3. Builds the host extension and UI library with `-Dversion=<version>` (without `-Dtest=true`, so dev buttons are hidden).
4. Renames the binaries to platform-specific names (e.g., `reaper_c1-linux-x86_64.so`).
5. Bundles maps and JSFX into a full archive.
6. Uploads both the individual binaries and the full archive as artifacts.

After all platforms finish, a release job collects everything and creates a GitHub release with:
- Individual binaries per platform (used by ReaPack for direct download)
- Per-platform `.tar.gz` archives (used for manual install)

## Generating the ReaPack index

The ReaPack index is an `index.xml` file that describes all packages in the repository. It is generated by `reapack-index` from the manifest files committed to the repo.

> **Not published yet.** Both manifests below start with `@noindex`, so
> `reapack-index` skips them. This matters because the monorepo's root
> `index.xml` is generated by scanning the whole repository: without
> `@noindex`, the next index rebuild would publish Console1 to every
> subscriber of the scripts repository. Before the first release, update the
> download URLs to the monorepo's `console1-v*` releases, add `reaper_mft`,
> then remove `@noindex`.

The manifest files are:
- `Extensions/Console1.ext` — describes the platform binaries, with download URLs pointing to GitHub release assets.
- `Perken/Console1 Maps.data` — describes the map files, served directly from the repo.
- `Effects/Perken/SumChannel S2 (Tukan).jsfx` — the patched JSFX, served directly from the repo.

To generate the index after a release:

```bash
cd zigwrap
reapack-index --rebuild --commit
git push
```

The `--rebuild` flag scans the entire git history and regenerates the index from scratch. The `--commit` flag creates a git commit with the updated `index.xml`. Push the commit so the index is available at the raw GitHub URL.

To validate without generating:

```bash
reapack-index --check
```

The version numbers in the `.ext` and `.data` manifest files must be updated before tagging. When preparing a release:

1. Update `@version` in `Extensions/Console1.ext`.
2. Update `@version` in `Perken/Console1 Maps.data`.
3. Update `@version` in `Effects/Perken/SumChannel S2 (Tukan).jsfx` (if the JSFX changed).
4. Commit these changes.
5. Tag and push.
6. After the CI release is created, run `reapack-index --rebuild --commit && git push`.

## Distributing to testers via ReaPack

Testers need to add the repository URL to their ReaPack configuration. The URL points to the raw `index.xml` in the repo:

```
https://raw.githubusercontent.com/AntoineBalaine/reaperConsole1/main/index.xml
```

Because the repo is private, testers need to have GitHub access to the repo (as collaborators). The raw URL will work for authenticated users via the GitHub personal access token that ReaPack uses.

If authentication is an issue, you can host the `index.xml` elsewhere (e.g., a simple web server or a public gist) and point `--url-template` at the release assets. But for an alpha with a few trusted testers, repo access is the simplest path.

To add the repository in REAPER:
1. Install ReaPack in REAPER (from https://reapack.com).
2. Go to `Extensions > ReaPack > Import repositories`.
3. Paste the `index.xml` URL.
4. Go to `Extensions > ReaPack > Browse packages` to see the Console1 packages.
5. Right-click and install.

ReaPack will download the correct binaries for the tester's platform and place them in `UserPlugins/`. The maps will be placed in `Data/Perken/Console1/maps/`. The JSFX will be placed in `Effects/Perken/`.

## Distributing to testers via manual install

For testers who don't want to use ReaPack, they can download the `.tar.gz` archive for their platform from the GitHub releases page and install manually:

1. Download `reaper-c1-<platform>.tar.gz` from the release page.
2. Extract the binaries (`reaper_c1.dylib/so/dll` and `reaper_c1_ui.dylib/so/dll`) into REAPER's `UserPlugins/` directory.
3. Extract the `maps/` directory into `<REAPER resource path>/Data/Perken/Console1/maps/`.
4. Optionally extract the `jsfx/` directory into `<REAPER resource path>/Effects/Perken/`.

Default REAPER resource path locations:
- macOS: `~/Library/Application Support/REAPER/`
- Linux: `~/.config/REAPER/`
- Windows: `%APPDATA%\REAPER\`

## Updating an existing release

If a release needs to be fixed without bumping the version:

1. Delete the tag and release on GitHub.
2. Fix the issue and push.
3. Re-tag with the same version and push the tag.
4. The CI will create a new release.
5. Regenerate the ReaPack index: `reapack-index --rebuild --commit && git push`.

For a new version, follow the normal release process with an incremented version number.
