# Data structures 

1. the application data (SUT): state, preferences, mapstore, mappings_list. 
    _This section represents 20k LOC of code by now and can’t be ported to external structs. This WILL have to go through a C wrapper to be queryable from rapidcheck._
2. the reaper model: hidden behind the mock API. Includes session/track/fx/param model, mock midi i/o. 
   _this part is vital for the application: the mocks must be in place and ready to be queried for the application to behave normally. Since the model’s written in zig currently, we’d also have to expose a C wrapper for the `command-apply()` functions of rapid-check - IF we need to query the reaper-model’s data (not sure about that).
   ## Options for interacting with the C side:
   1. direct export of mock functions using `export fn`
   2. export mock state query functions `export fn mock_reaper_get_track_count()` etc. Preferable.
   3. export the reaper API module, with substitutions for the function pointers. Bringing the mocks back to the C side is difficult.
3. the C1 model: just an array of values that can be accessed from th mock midi i/o. This is POD, and probably easy to move across the language-boundary.
4. the `InitialStateConfig`, which contains all the initially-generated data for each test run. Needs to flow across the language boundary, so it might be preferable to pass it to zig as a C struct.
5. RapidCheck Components (C++ Side)
- StateModel: Simplified model of the expected state.
- StateSystem: Wrapper around the Zig test environment (basically a struct that holds the opaque pointer to the globals object.)
- Command classes: Define what actions can be taken and how they affect both model and system. One command per action (they could be grouped by category at a later time)


# Flow 

`InitialStateConfig` is generated by rapidcheck. the struct gets passed over to the zig side. zig instantiates the mocks and SUT using initialstateconfig’s data. CPP side instantiates the state model with the same data. 
The test runner generates a sequence of commands, applies them to the model, and runs them over the SUT to compare.

# Payload generation

Given that the main entry point to trigger actions is going to be through the actions’ dispatch function, I reckon that it might be a good idea to start by looking at how to generate the payloads.

For payload generation it’d tricky to construct the payload entirely: I don’t know whether it would be possible to generate zig’s `union(enum)` with payloads in the variants, with the same memory layout, across the language boundary. We’d be better off generating **parameters**.
We want to keep separate APIs for app state and mock state - reaper’s model and its query api have to be re-usable for other projects, and  in fact, the reaper module is already self-contained. So far, when testing, all that the model does upon instantiation is replace the original function pointers with pointers to the mock functions. There’s a trick, there though: while it would be nice to be able to query the reaper API module from the CPP side, I don’t know how to make it work: they’re meant to be linked at compile time with the declarations from the reaper_plugin_functions.h, and substituted for non-null pointers at runtime by the host (or the test model). So either we have to figure out a way for Cpp side to re-use the linking during test runs, or we have to expose the mock functions through a wrapper other than the reaper API module - or by straight-up exporting them, which is possible since the data return types are all c primitives. Any recommendations?

# Order of implementation

- settings actions @settings_actions.zig (no model interaction, few data changes)
- csurf actions @csurf_actions.zig 
    queries on both models, mainly on C1. Requires generating one fx mapping per action, and sending data to the reaper model. Doesn’t trigger track validation, though.
- fx_ctrl @fx_ctrl_actions.zig 
   queries on both models. Requires generating fx mappings. Some of the actions trigger mode changes, but they don’t have to be implemented first.
- track list actions @tracklist_actions.zig
    queries on both models, triggers track validation - which involves the whole track state, all fx mappings, and calling getters and setters on the reaper model.
- fx_sel actions @fx_sel_actions.zig 
   queries on both models, calls setters on the session model, and triggers track validation.
- transport actions @transport_actions.zig 
    not priority, mostly interacts with the timeline.
