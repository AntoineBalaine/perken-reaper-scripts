# Contributing to the extensions

How to build, test, extend and debug the compiled extensions. For what each
extension is and how they fit together, read [ARCHITECTURE.md](ARCHITECTURE.md)
first.

## Setting up

You need:

- **Zig**, in the series pinned by each extension's `.zigversion` (currently
  0.17.x; any patch release works). The install scripts refuse a mismatching
  compiler; pass one with `-z /path/to/zig`.
- **REAPER's own C++ compiler**, for the extensions that contain C++
  (`perken-utilities`, `console1`): Apple clang on macOS, `gcc` on Linux,
  `cl` on Windows. Zig's bundled clang cannot replace it; the reason is in
  the last section of [README.md](README.md).
- **PHP**, for `console1` only. SWELL's dialog resources are generated by a
  PHP script during its build.
- **ReaImGui**, inside REAPER, for the windows (the whichkey, the tempo
  window, the action palette). It is installed through ReaPack.
- **Docker**, optionally, to run the Linux CI steps locally (see
  [README.md](README.md)).

Build and test each extension from its own folder:

| Extension | Test | Build |
|---|---|---|
| `reaziglib` | `zig build test` | none |
| `reavim-ext` | `zig build test` | `zig build` |
| `perken-utilities` | `zig build test` | `zig build` |
| `console1` | `zig build test -Dtest=true` and `zig build mft-test` | `zig build`, `zig build ui`, `zig build mft` |
| `vr09` | `zig build test` | `zig build` |

Because the other extensions use `reaziglib` from source, a change to it can
break any of them. Run the tests of every extension that uses the file you
changed, not only of the one you are working on.

Run `zig fmt src` before a commit. Commit messages start with the area, for
example `perken-utilities: …` or `reaziglib: …`.

To try a build in REAPER, use `extensions/build-install.sh` (see
[README.md](README.md)). It keeps a keymap you have edited. To install into a
scratch folder instead of your own REAPER, set `REAPER_RESOURCE_PATH`.

## Adding an action

### In `perken-utilities`

Each module exports an `entries` table of named actions
(`actions.Entry`), and `main.zig` registers every entry in REAPER as
`Perken: <description>` with the command id `_PERKEN_<name>`. An action is a
list of steps: a numeric REAPER command (`.cmd`), a named command such as an
SWS one (`.named`), or a Zig function (`.func`).

```zig
fn sayHello(_: *actions.RunCtx) void {
    Reaper.ShowConsoleMsg("hello\n");
}

pub const entries = [_]actions.Entry{
    .{ .name = "SayHello", .def = .{
        .steps = &.{.{ .func = &sayHello }},
        .desc = "Say hello", // the name in REAPER's action list
    } },
};
```

Then:

1. Add the module to `all_entries` in `main.zig` (a test fails if two actions
   share a name), and to the `test` block at the end of that file, so that its
   tests run.
2. Add every REAPER function the action calls to the `reaper_api` list in
   `main.zig`. Extensions resolve only the functions they list, and a missing
   one is a null pointer at run time. A unit test in each extension's
   `main.zig` scans the sources and fails on a function that is not listed.
3. Add `; <keys> = _PERKEN_SayHello` to the default keymap
   (`reavim-ext/src/default_bindings.ini`). Entries for Perken Utilities ship
   commented out, so that the keymap works without it installed.

Set `.midi_command = true` for an action that belongs in the MIDI editor, and
`.toggle_state` for an on/off action whose state REAPER should show on
toolbar buttons.

### In `reavim-ext`

Vim-grammar actions are registered in `src/defaults_actions.zig`. Native
implementations live in `src/ported/`. An action is bound in
`src/default_bindings.ini`, under the section that matches its role
(`[main.command]`, `[main.track_motion]`, `[main.timeline_operator]`, …); the
role decides how it combines with other keys, see the grammar summary in
[ARCHITECTURE.md](ARCHITECTURE.md). Test new sequences in
`src/builder.zig`.

## REAPER API: things that will bite

- **A function must be in the extension's `reaper_api` list** (see above), or
  it is never loaded. `zig build test` catches a forgotten one, as long as the
  call is written `Reaper.Name` or `reaper.Name`.
- **Some bindings in `reaziglib/src/reaper.zig` are mistyped.** The handle
  types (`MediaItem`, `MediaTrack`, …) are already pointers, yet functions
  take `*MediaItem`; and functions that return NULL are declared as
  returning a non-optional. `ReaProject` is an opaque handle, and every
  function that takes a project accepts `?ReaProject`, so `null` means the
  active project. Code works around it
  with the casts and shims in `reaper_helpers.zig`. **When you need a binding
  that is wrong, fix the binding and its callers; do not add another shim.**
  The keyboard-section functions were fixed that way, as a model.
- **ReaImGui may load after your extension** (plugin files load in name
  order), so resolve its API on the first timer tick, as the whichkey and the
  windows in `perken-utilities` do, and treat "not installed" as a normal case.
- **Windows cannot use `std.fs`'s absolute-path calls** at the depth REAPER
  calls into an extension (they overflow the stack); `reavim-ext` has
  `win_file.zig` for this.
- **SWELL exists on macOS and Linux only.** Code that calls it, such as
  Console1's dialogs, does not compile for Windows yet.
- **C++ that REAPER calls through virtual methods** must be built with
  REAPER's toolchain, through `reaziglib`'s `reaperCxxObject` (see
  [README.md](README.md)).
- **Extensions can register actions and hooks, but cannot be tested inside
  REAPER by the build.** Behaviour in REAPER is checked by hand.

## Testing and debugging

- The unit tests cover the logic that does not need REAPER: the grammar and
  keymap parsing, the fuzzy matcher, the beat tracker, the file formats. They
  do not run REAPER. Anything that calls the REAPER API is verified by trying
  it in REAPER.
- Logs are scope-prefixed (`(engine)`, `(accel)`, `(rename)`, …) and go to
  standard error. Launch REAPER from a terminal to see them
  (`/Applications/REAPER.app/Contents/MacOS/REAPER` on macOS). A Debug build
  of `reavim-ext` logs every key and the result of every command. Release
  builds log less: `perken-utilities` logs at `info` in a `ReleaseSafe` build,
  at `warn` in `ReleaseFast` and at `err` in `ReleaseSmall`.
- `reavim-ext/AGENTS.md` describes an optional headless setup (Xvfb and
  xdotool on Linux) for driving a real REAPER from a script.

## Dependencies

Each extension's `build.zig.zon` pins its dependencies by commit:

| Dependency | Used for | By |
|---|---|---|
| `ini` (a fork) | Reading `.ini` files | all of them |
| `WDL` | SWELL, REAPER's Win32 emulation on macOS and Linux | `reavim-ext`, `console1` |
| `reaper-sdk` | REAPER's C++ headers | `console1` |
| `qm-dsp` | Beat tracking for the tempo tool (GPL) | `perken-utilities` |
| `zlowcheck` | Property-based tests | `console1` |
| `libhegel` | Property-based tests (test-only) | `perken-utilities` |

To update one, run `zig fetch --save <url>` in the extension's folder, which
rewrites the URL and the hash.

`libhegel` is the exception: `zig fetch` rejects GitHub's raw release assets
(unsupported `Content-Disposition`), so `perken-utilities/build.zig` pins the
release tag itself and `tools/fetch_hegel.zig` downloads the right platform's
static archive, checked against the release's published `.sha256`. To move to
a newer release, change `hegel_tag` in `build.zig`.

Because those archives are tens of megabytes, `-Dhegel-lib-dir=<path>` (or
`$HEGEL_LIB_DIR`) keeps one between builds and downloads only when it is
absent. The workflow passes `.hegel-cache` and caches that directory, keyed
on `build.zig`, so bumping the tag misses the cache exactly once.

## Continuous integration

There is one workflow per extension in `.github/workflows/`. A branch push or
pull request builds an extension when its folder, `reaziglib` or its workflow
changes; a tag (`<extension>-v<version>`) also releases. Things to know:

- macOS jobs are pinned to `macos-15`. On the newer `macos-26` image, Zig
  0.14 links nothing from the C library.
- GitHub retired the Intel macOS runner, so the x86_64 macOS binaries are
  cross-built on `macos-15`; their tests run only on the arm64 row.
- Windows builds use the MSVC toolchain from a Visual Studio developer
  environment. The Windows rows for Console1 and MIDI Fighter Twister are
  removed until their code is ported.
- A failing job's log is the first thing to read. The Linux and macOS steps
  can be reproduced locally with `extensions/linux-ci/linux-ci.sh` and the
  commands in the table above.
